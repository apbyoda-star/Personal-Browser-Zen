# Native-Parity Audit — Vector features vs. Firefox/Zen natives

**Status:** Audit only. No code written. Companion to `MIGRATION_PLAN.md`; where the two disagree, the disagreement is flagged loudly in §8 — this audit re-derived every bucket from evidence rather than trusting the plan.

**Evidence base (how verdicts were verified, since `engine/` is not downloaded yet):**
- The Zen fork's `.patch` files diff against *real* Firefox 154 files, proving those files/APIs exist; `src/zen/@types/lib.gecko.*.d.ts` are generated from real mozilla-central IDL (interfaces cited below were found verbatim there); `prefs/**.yaml` carry real pref names.
- Zen's own modules were read directly (line counts via `wc -l`; pref names quoted verbatim from `prefs/zen/*.yaml`).
- MDN / searchfox / bugzilla for WebExtension API behavior in Firefox specifically.
- Intent-vs-workaround evidence: Vector's full git history (218 commits, 2026-06-19 → 2026-08-07), all of `COORDINATION.md` (739 lines), `CODE-ISSUES.md`, `context.md`, and code comments — quoted where load-bearing.

**Verdict key:** `DELETE — native` · `CONFIG — native + pref` · `RESKIN — native + CSS` · `EXTEND — build on Zen` · `PORT — genuinely custom` · `DROP — not worth it`

**Headline:** Of ~75 audited items, only **~14 are true PORTs**, and nearly all of those are the shop/Slack/AI *application* logic — genuinely yours, with no possible native equivalent. Almost everything browser-shaped is DELETE / CONFIG / RESKIN / EXTEND. Three "companion service required" verdicts from the plan are **downgraded or reversed** by chrome-privilege findings (§8).

## 7. Cross-cutting security note

Secrets currently `safeStorage`-encrypted (Slack tokens, Gemini key, OAuth refresh tokens, card PAN/CVV, Supabase key): anything living in the **fork's chrome layer** keeps keychain-grade storage via `OSKeyStore` (§1.10) — no regression. Anything living in the **WebExtension** lands in `storage.local` unless the fork exposes a custom privileged API to the bundled extension (see §8-D5) or a native-messaging keystore is used. This asymmetry should drive *where* each integration lives.

## 8. LOUD DISAGREEMENTS — audit vs. MIGRATION_PLAN.md

Where this audit's evidence contradicts the plan's bucket. **The audit's verdicts supersede** pending your review.

- **D1 — UDP LAN nudge.** Plan: "companion required — WebExtensions have no UDP." Audit: **`nsIUDPSocket` is fully scriptable from chrome JS** including multicast (interface verified in the fork's own type defs). In a fork, the nudge can live in the chrome layer — no companion. Remaining question is only *plumbing* (how the shop WebExtension reaches chrome — see D5) and a broadcast-address test.
- **D2 — Slack always-on-top interrupt popup.** Plan: "no in-browser story; native companion required." Audit: **chrome `window.open(…"alwaysontop"…)` maps to `CHROME_ALWAYS_ON_TOP`** — the same mechanism Picture-in-Picture ships on, floating over other apps on Windows and macOS; Zen itself opens an `alwaysontop` chrome window (`ZenBoostsManager.sys.mjs:647`). Caveats that keep this from a clean flip: macOS join-all-Spaces is set in PiP's widget code (not JS-exposed — may need a tiny C++ patch, which a fork can carry), never-steal-focus needs verification, Linux/Wayland is best-effort. **Verdict downgraded from "companion required" to "chrome-layer with a possible small widget patch."**
- **D3 — Silent/tray printing (TYC cards, AR statements, dispatch list).** Plan: "extensions can only window.print(); companion for silent/tray." Audit: **`nsIPrintSettings.printSilent` + `printerName` + `nsIPrinterList` are chrome-scriptable** (verified) — a fork can print silently to a named printer/tray from chrome JS. Also, intent-evidence shows several Vector paths are deliberately NOT silent ("the OS print dialog is the confirm step" — `callbacks-workflow.ts:727`), shrinking the silent-print requirement further.
- **D4 — Wallboard.** Plan: "content-script visibility spoof + kiosk profile." Audit: **`browser.docShellIsActive=true` / `forceAppWindowActive`** (both verified; the first proven used by Zen) makes the page genuinely 'visible' to Gecko — no spoof, no content script. Chrome-owned window + two prefs.
- **D5 — The companion service itself.** Plan recommended one companion for UDP + printing + keychain + Slack popup. After D1–D4, **every one of its four jobs has a chrome-layer path**. The honest remaining question: the shop suite is best built as a WebExtension (content-script ergonomics), and a WebExtension can't call chrome APIs — the bridge options are (a) fork-defined privileged extension APIs (WebExtension Experiments shipped in-tree — a fork can do this), (b) native messaging to a companion, or (c) move the few privileged bits (UDP, print, keystore) into chrome modules that the extension reaches via a tiny fork-provided API. **Recommendation flip: default to no companion; decide (a)/(c) at implementation.** Also note: `surfer.json addons` bundling has **zero in-tree precedent** — spike it early (this risk was NOT in the plan).
- **D6 — FolderPeek.** Plan: "new chrome module." Audit: **Zen already ships hover-search on collapsed folders** (`zen.folders.search.enabled`, 500ms delay, searchable tab popup). Verdict → CONFIG+RESKIN with small extensions, not a new module.
- **D7 — Drag-and-drop engine.** Plan: "port Vector's pointer-based engine." Audit: **Zen's `ZenDragAndDrop.js` (1,831) already replaces Firefox tab-drag** with custom visuals, folder/essentials targets, mid-drag space switching. Verdict → EXTEND/RESKIN; porting Vector's engine would duplicate a maintained system — exactly the failure mode this audit exists to prevent.
- **D8 — Command box + gradient picker.** Plan treated both as fresh bucket-B builds. Audit: Zen's floating urlbar + quick-actions provider + results learner, and Zen's per-space gradient picker (color wheel, custom colors, textures) already cover the majority. Verdict → EXTEND + RESKIN.
- **D9 — Pinned-tab sleep/reset semantics.** Plan: "custom bucket-B build on gBrowser." Audit: **Zen's `ZenPinnedTabManager` implements Vector's exact model** (stored pinned URL, reset-unload-switch on close, changed-indicator with reset button). Verdict → CONFIG + RESKIN.
- **D10 — Google OAuth.** Plan: "loopback flow impossible without native host; switch client type." Audit: Firefox's `identity.getRedirectURL()` **accepts a loopback form** (`http://127.0.0.1/mozoauth2/…`, Fx 86+) for providers requiring verified domains — the Desktop-client model may survive unchanged. Verify against Google's current client-type rules at implementation.
